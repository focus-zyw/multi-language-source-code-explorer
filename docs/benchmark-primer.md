## 第 0 章 这个项目到底在解决什么问题

### 0.1 一个你肯定遇到过的场景

你 clone 了一个陌生项目，想搞清楚"用户登录是怎么实现的"。

**传统做法**：

1. 全局搜索 `login`，出来 20 个文件；
2. 打开第一个，看到它调用了 `authenticate()`；
3. 点进去（其实是复制名字再搜一次），又跳到第三个文件；
4. 看了五行，忘了自己从哪来的；
5. 想回去，只能按浏览器的后退键——然后发现搜索状态没了。

**Code Atlas 的做法**：

1. 导入这个项目（本地路径、文件夹或 ZIP）；
2. 左侧列出所有函数/方法，按复杂度、被调用次数排好序；
3. 点一个方法，右边是源码 + 这个方法调用了谁（可点击）+ 它的流程图 + 关键变量；
4. 一路点下去，顶部一直记着你的探索路径，随时能退回起点；
5. 卡住了，点"生成 AI 讲解"，让模型基于这个方法的源码和静态事实讲一遍。

一句话概括：**它把一整个代码仓库，变成一张可以点着读的地图。**

纸质地图只能告诉你"这条街在哪"；导航 App 还能告诉你"这条路通向哪、哪条最堵、你现在在哪"。
Code Atlas 想做后者。

### 0.2 它明确不做的三件事（这点很重要）

理解一个工具，先理解它的边界。

| 不做 | 原因 |
| --- | --- |
| **不运行你的代码** | 导入、浏览、AI 分析全部是"读文本"，不执行。唯一例外是你在"测试"页签手动勾选确认后跑测试，且需要先在 `.env.local` 里打开开关 |
| **不修改你的代码** | 全程只读。没有"重构""自动修复"这类功能 |
| **不承诺 100% 准确** | 这是静态分析的物理上限，不是偷懒。详见 2.1 节 |

第三条最容易被误解，但它恰恰是这个项目最值得尊重的地方——**它会明确告诉你"这条关系我不确定"**，
而不是假装什么都知道。

### 0.3 它内部的三段流水线

不管你导入的是 Python 还是 Go，内部都走同一条流水线：

| 阶段 | 输入 | 做了什么 | 输出 |
| --- | --- | --- | --- |
| **① 读进来** | 一个文件夹 | 遍历文件，跳过 `node_modules`、`.git`、二进制、超过 1MB 的文件 | 一堆"值得分析"的源码文本 |
| **② 拆成符号** | 源码文本 | 用语法解析器把文本变成树，从树里挑出函数、类、方法、测试 | 符号列表 + 每个符号的精确位置 |
| **③ 连关系并展示** | 符号列表 | 把 `foo()` 这个名字对应到"到底是哪个 foo"，标上可信度，存进数据库 | 可以点击的调用关系、流程图、AI 讲解 |

第 ② 步和第 ③ 步是全部技术难度的所在。下面两章就讲这两步。

## 第 1 章 从"一堆文本"到"可以点的地图"

### 1.1 第一步：为什么要过滤

一个普通的 Node 项目，`node_modules` 里可能有 **20 万个文件**。
如果把它们全解析一遍：几小时起步，数据库爆掉，而且——那不是"你的"代码，是别人写好的库。

所以导入时会跳过：`node_modules`、`.git`、`dist`/`build` 产物、`__pycache__`、虚拟环境、
`.d.ts` 类型声明、压缩后的产物（`.min.js`）、二进制文件、非 UTF-8 文件、超过 1MB 的单文件。

**被跳过的内容会在导入报告里列出来**，附原因。这一点值得学：过滤是必要的，但**悄悄过滤**是危险的
——你会以为自己看完了整个项目。

### 1.2 第二步：把文本变成"语法树"

这是全篇最重要的概念，请慢一点读。

#### 先看一个反例：为什么不能用字符串匹配

```python
def greet(name):
    if name:
        return "hi " + name
    return "hi"
```

假设你想知道"这个文件里有哪些函数"。用搜索 `def ` 好像可行。

但如果代码里有一行注释：

```python
# 以前这里有个 def old_greet()，后来删了
```

或者一个字符串：

```python
message = "请实现 def parse() 方法"
```

字符串匹配就会把它们误判成函数。反过来，如果代码写成 `def  greet(name)`（两个空格），
或者跨行写成：

```python
def greet(
    name,
):
```

字符串匹配又会漏掉。

**根本问题**：文本本身没有"结构"，只有字符的排列。你需要一个东西告诉你
"这一段是一个函数定义，它的名字是 greet，它的参数是 name"。

#### 什么是语法树（AST）

把代码按语法规则拆开，变成一棵树。上面那段代码拆出来大致是这样（已简化）：

```
function_definition            ← 这是一个函数定义
├── name: "greet"              ← 名字叫 greet
├── parameters
│   └── identifier: "name"     ← 有一个参数叫 name
└── body                       ← 函数体
    ├── if_statement
    │   ├── condition: "name"  ← 条件
    │   └── consequence
    │       └── return_statement
    │           └── binary_operator: "hi " + name
    └── return_statement       ← 最后那个 return "hi"
        └── string: "hi"
```

这棵树叫 **AST**（Abstract Syntax Tree，抽象语法树）。"抽象"是因为它丢掉了空格、换行、
注释这些对结构没用的东西，只保留"谁包含谁"。

有了这棵树，问"有哪些函数"就变成了"找出所有 `function_definition` 节点"——
**精确，不会误判，也不会漏**。

#### tree-sitter 是什么

每种语言的语法规则不一样，所以理论上要为每种语言写一个解析器。这是巨大的工作量。

**tree-sitter** 是一个通用的语法解析框架：它把"语法规则"和"解析引擎"分开。
每种语言的规则写成一份语法定义（grammar），编译成一个小文件；引擎负责用这份规则去解析代码。
目前社区已经有几十种语言的现成语法包。

对本项目来说，它的价值是：**同一个接口，能解析 8 种语言**。
你在 `analysis/lang/python.ts` 和 `analysis/lang/go.ts` 里看到的代码结构是相似的，
因为它们调用的是同一个解析器，只是遍历的节点类型不同。

#### WASM 是什么，为什么要用它

**WASM**（WebAssembly）是一种"可以在任何地方跑的二进制格式"。原本是为了让 C++/Rust 写的程序
能在浏览器里跑，但现在 Node.js 也支持。

为什么本项目用它：tree-sitter 的解析引擎是 C 写的。传统做法是用 Node 的原生模块（native addon），
需要在你机器上现场编译（node-gyp），Windows 上经常因为缺 Visual Studio 编译工具而失败。

用 WASM 版本（`web-tree-sitter` + `tree-sitter-wasms` 提供的语法包）就**不需要任何编译**，
`npm install` 完就能跑。代价是稍慢一点，但对个人工具完全够用。

这个取舍在 `README.md` 的"与建议技术栈的差异"里有说明，也是理解整个项目设计取向的钥匙：
**宁可慢一点，也不要"装不上"**。

### 1.3 第三步：从树里挑出"符号"

**符号（Symbol）** 是这本书里的"词条"：一个有名字、可以被别人指向的东西。

在本项目里，符号包括：

| 类型 | 例子 |
| --- | --- |
| `function` | `def parse_config(path):` |
| `method` | `class User { login() {} }` 里的 `login` |
| `class` | `class OrderService` |
| `test` | `it("should login", ...)`、`def test_login():` |
| `element` | HTML 里的 `<div id="app">` |
| `property` | JSON 里的 `$["scripts"]["dev"]` |

每个符号会记下：名字、限定名（`OrderService.login`）、参数、返回类型、文档注释、
装饰器/注解、复杂度指标，以及**精确到字符的位置**（第几行第几列到第几行第几列）。

为什么要记"字符位置"而不只是"行号"？

因为源码可能被裁剪展示（"只看这个方法"模式），也可能同一个文件里有两个同名方法。
字符偏移是唯一不会歧义的位置表示。

### 1.4 第四步：把名字对应到定义（最难的一步）

这一步叫**引用解析**（name resolution），是整个项目最复杂的部分，
`src/lib/analysis/resolve.ts` 有 656 行，全在处理这一件事。

#### 问题长什么样

```python
client = get_client()
client.get("/users")
```

看到 `client.get()`，你要回答：**这个 `get` 到底是哪个类的方法？**

人类会看上一行 `get_client()` 返回了什么。但静态分析不能"运行"代码，它只能读。

#### 三种可能的情况

| 情况 | 代码长什么样 | 能不能确定 |
| --- | --- | --- |
| **能确定** | `import requests` 然后 `requests.get(...)` | 能。导入语句明确说了 `requests` 是哪个包 |
| **能推断** | `client: HttpClient = ...` 然后 `client.get()` | 大概能。有类型标注，但如果运行时被替换就错了 |
| **只能猜** | `obj = factory()` 然后 `obj.run()` | 不能。`factory()` 返回什么，静态看不出来 |

更麻烦的情况还有：反射（`getattr(obj, name)()`）、依赖注入（框架在运行时塞对象）、
回调（函数当参数传进去，不知道谁调用）、`monkey patch`（运行时改类的方法）。

#### 本项目的处理方式

它不假装自己能解决所有情况，而是**给每条关系标一个可信度**。这就是第 2 章的第一个概念。

### 1.5 第五步：存进数据库

项目用 SQLite（一个"就是一个文件"的数据库，不需要装服务）。核心 6 张表：

| 表 | 存什么 | 打个比方 |
| --- | --- | --- |
| `files` | 每个文件的路径、语言、完整源码 | 书的正文 |
| `symbols` | 每个函数/类/方法的信息 | 书的词条 |
| `refs` | "这个方法里出现了一次调用" | 词条里的"参见"标记 |
| `ref_targets` | "这次调用指向了哪个符号，可信度多少" | "参见"具体指向哪一页 |
| `test_links` | "这个测试在测哪个方法" | 习题和知识点的对应关系 |
| `symbol_explanations` | AI 生成的讲解 + 指纹 | 别人写的读书笔记 |

`refs` 和 `ref_targets` 为什么要分成两张表？

因为一次调用可能对应**多个候选**。比如 Java 里同名方法有 3 个重载，
或者按名字猜到了 2 个同名函数。`refs` 记"这里有一次调用"，
`ref_targets` 记"它可能指向 A（确定）、B（猜测）、C（猜测）"。

这个设计很关键：**它让"不确定"有了地方存放**，而不是被迫二选一。

## 第 2 章 三个必须先懂的概念

### 2.1 可信度：为什么"我不确定"比"我猜"更有价值

#### 导航的类比

假设你开车，导航说：

- **"前方 200 米右转"** —— 它确定。你会照做。
- **"可能是前方第二个路口右转"** —— 它有依据（比如地图数据），但没验证。你会放慢速度。
- **"我猜是前面那条小路"** —— 纯猜。你大概会自己看一眼。

如果一个导航**把三种情况都说成"右转"**，短期看很"智能"，长期看你会失去对它的信任。

代码分析工具一模一样。

#### 本项目的五级

| 级别 | 中文 | 什么时候会给这个级别 | 你该怎么用 |
| --- | --- | --- | --- |
| `exact` | 确定 | 语法结构直接可见、import 明确绑定、同文件定义、`self.x`/`this.x` 所属类 | 可以当事实 |
| `inferred` | 推断 | 有类型标注、`x = Foo()` 构造、继承链、路径别名 | 大概率对，注意运行时可能变 |
| `heuristic` | 候选·猜测 | 只按方法名匹配、项目内同名 | 只是线索，必须自己看源码 |
| `external` | 外部/内建 | 标准库、第三方包 | 项目外，不追进去 |
| `unresolved` | 无法解析 | 动态调用、找不到定义 | 明确告诉你"这里我没搞懂" |

UI 上用颜色区分：确定是绿色实线，推断是蓝色实线，猜测是黄色虚线，
外部是灰色点线，无法解析是红色波浪线。

**这个设计的深层意义**：静态分析工具最大的失败模式不是"漏掉"，而是"编造"。
一个编造出来的调用关系会让学习者建立错误的心理模型，而且很难发现。
把"不确定"显式标出来，是把判断权交还给读者。

### 2.2 指纹：为什么改一行代码不该让 AI 讲解作废

#### 问题

AI 讲解要花钱、花时间。你昨天给 `parse_config` 生成过讲解，今天在文件**开头**加了一行
`import os`，方法本身一个字没改。如果讲解因此失效，你会很烦。

#### 什么是"指纹"（哈希）

哈希函数能把任意长度的内容，压成一个固定长度的字符串。特点是：

- 同样的内容 → 永远得到同样的指纹；
- 内容改一个字符 → 指纹完全变样；
- 没法从指纹反推出内容。

就像人的指纹：能唯一标识一个人，但看不出这个人长什么样。

#### 本项目的做法

生成讲解时，把"讲解依赖的所有东西"拼起来算一个指纹：

```
文件路径 + 语言 + 方法完整源码 + 签名 + 文档注释 + 度量 + 调用关系（含可信度）
→ sha256 → 一串 64 位十六进制
```

下次打开时，重新算一遍。指纹一样 → 直接读缓存；不一样 → 需要重新生成。

#### 一个精妙的小细节：相对行号

指纹里记录调用位置时，用的是**方法内相对行号**，不是文件绝对行号。

```
绝对行号：文件第 152 行有一次调用  ← 前面插一行，就变成 153，指纹变了
相对行号：方法内第 8 行有一次调用  ← 前面插一百行，还是第 8 行，指纹不变
```

代价是：老版本的讲解里存的是绝对行号，所以迁移时还要额外核对位置没变。
这个兼容逻辑在 `explanation-fingerprint.ts` 里，版本号 1/2/3 就是在标记不同的指纹规则。

### 2.3 为什么"符号 ID"会变，以及它带来的麻烦

这个坑很隐蔽，但影响很大。

数据库里每个符号有一个 `id`，是自增整数：1、2、3…… 就像**座位号**。

问题是：每次"重新扫描"项目，实现方式是**先把旧数据全删了，再全量插入新的**。
于是座位号会重新发一遍：

```
重扫前：id=3 → OrderService.login
重扫后：id=3 → UserRepository.save     ← 同一个座位，换了个人
        id=7 → OrderService.login       ← login 换到了 7 号
```

结果：

- 你收藏的书签记着"3 号"，重扫后指向了别的方法；
- AI 讲解缓存在 3 号上，重扫后对不上了；
- 问答记录也记着 3 号。

现在的解决办法是"用路径 + 限定名 + 源码摘要重新找回来"。
这能工作，但很脆弱：方法改名了、移动文件了、同名方法有两个，都会失败。
而且这套"找回来"的逻辑在三个地方各写了一遍。

**根因是：用座位号当身份证。** 第 4.2 节讲怎么修。

## 第 3 章 那 40 多个 GitHub 项目分别是什么

光看 star 数没有意义——90k star 的 Mermaid 和 16k star 的 Sourcetrail，
对本项目的价值完全不是一回事。下面按"门派"分类，每个说清**它解决什么问题**。

### 3.1 老前辈：Sourcetrail（16.5k star，已归档）

**它做什么**：2016 年前后出现的开源"交互式源码浏览器"。导入一个 C++/Java/Python 项目，
生成一个可以点击的图：点一个类，看到谁继承了它、谁调用了它、它包含了哪些文件。
双击跳到源码。

**为什么它是"最像的前辈"**：它的产品形态和 Code Atlas 几乎一模一样——
索引器 + 数据库 + 图形化探索 + 源码联动。它还发明了一个叫 **Active Trail** 的概念：
你探索过的符号会排成一条路径，可以随时跳回任何一步。

**为什么没继续用**：它依赖 clang（C++ 编译器前端）做解析，装起来极重，
而且 2021 年底停止维护了。

**能学什么**：产品设计。特别是"探索路径"和"书签"怎么组织，它做得比很多现代工具都好。
**不能学什么**：它的解析架构。Code Atlas 用 WASM 就是为了避开它踩过的坑。

### 3.2 学术派：Glean / Joern / CodeQL / SCIP

这一派的特点是：**先把代码变成"事实"，再对事实做查询**。

| 项目 | star | 一句话 |
| --- | ---: | --- |
| **Glean**（Meta） | 1.4k | 把代码的各种事实（"X 是 Y 的子类""A 调用了 B"）存进数据库，用一个叫 Angle 的查询语言查 |
| **Joern** | 3.6k | 把 AST、控制流图、数据流图合成一张"代码属性图"（CPG），主要用来找漏洞 |
| **CodeQL**（GitHub） | 10.2k | 同上思路，用类 SQL 的语言写查询，是 GitHub 代码扫描的引擎 |
| **SCIP** | 834 | 不是工具，是一个**协议**：定义"怎么给代码里的每个符号起一个全局唯一的编号" |

**和本项目的关系**：前三个是"重型武器"，为了查漏洞设计的，学习曲线极陡，
和"帮人读懂代码"的目标不同。但 **SCIP 值得单独看**——它的符号编号方案正好能修 2.3 节那个坑。

### 3.3 工程派：OpenGrok / Doxygen / ctags / Sourcegraph

| 项目 | star | 一句话 |
| --- | ---: | --- |
| **OpenGrok** | 5.0k | 老牌源码搜索 + 交叉引用（xref）引擎，Solaris/Java 圈用得多 |
| **Doxygen** | 6.6k | 从注释生成文档，附带调用图、被调用图、包含图 |
| **ctags** | 7.3k | 只做一件事：扫描源码，输出"符号名 → 文件:行号"的索引文件。Vim 的跳转就靠它 |

## 第 4 章 四个最值得抄的点，逐个讲透

### 4.1 Repo Map：让 AI"先看一眼地图再回答"

#### 问题

现在的 AI 讲解，发给模型的东西大概是这样：

```
这是一个 method（语言：python，文件：src/config/loader.py，名称：merge_missing_defaults）
### 静态分析事实
- 圈复杂度 4，12 行，2 个参数
### 方法体内的调用及其解析可信度
- dict.update()（外部/内建）
### 源码
def merge_missing_defaults(...):
    ...
```

模型看到的是一页纸。你问它"这个方法在系统里的作用"，它只能根据函数名和参数猜。

#### 类比

你要给朋友介绍一栋楼里的某个房间。

- **现在**：只给他房间的照片。他能说清"这是个会议室，有投影仪"，但说不出"这栋楼是干嘛的"。
- **Repo Map**：先给他一张整栋楼的平面图（每层有哪些房间、哪些房间常被使用），再给房间照片。
  他立刻能说"这是三楼东侧的会议室，旁边是财务部，所以他们大概在开预算会"。

#### 什么是 PageRank（零基础版）

PageRank 是 Google 当年给网页排名发明的算法。核心思想极简单：**投票**。

- 一个网页被越多网页链接，它越重要；
- 但"重要"是递归的：被一个**重要的**网页链接，比被一百个垃圾网页链接更值钱。

算的时候是个迭代过程：

1. 一开始所有节点平分权重（比如 4 个节点，各 0.25）；
2. 每个节点把自己的权重**平均分给它指向的节点**；
3. 重复几十次，权重会收敛到稳定值。

用一句话记住：**谁被重要的人引用，谁就重要。**

#### Aider 怎么把它用在代码上

（以下机制读自 `aider/repomap.py` 源码）

1. **抽标签**：用 tree-sitter 查询每个文件里"定义了什么名字""引用了什么名字"。
2. **建图**：节点是**文件**，如果文件 A 引用了文件 B 里定义的名字，就连一条 A→B 的边。
   边的权重和"这个名字被引用了多少次"有关（开平方，防止高频词刷分）。
3. **加权**：
   - 当前正在聊的文件 ×50（它是主角）
   - 用户提到的标识符 ×10
   - 名字很长且是驼峰/下划线的（大概率是有意义的业务名）×10
   - 下划线开头的私有名 ×0.1
   - 被超过 5 个文件定义的名字（太常见，没区分度）×0.1
4. **跑 PageRank**，但**带偏好**：不是所有节点起点相同，而是给当前文件、用户提到的文件
   更高的初始权重。这叫 **personalized PageRank**（带个人偏好的 PageRank）。
5. **二分搜索**选出前 N 个，让渲染出来的骨架刚好塞进 token 预算。

#### 什么是 token 预算，为什么用二分

**token** 是模型计费和处理的最小单位。英文大约 4 个字符 = 1 token，中文大约 1 个字 = 1-2 token。
每个模型有上下文上限（比如 128k token），你不能无限往里塞。

**二分搜索**是个很朴素的技巧：假设你要从 500 个符号里选前 N 个。

- 先试 N=250，渲染出来一算，超了；
- 试 N=125，没超但还有空间；
- 试 N=187……
- 十几次就逼近最优值。

Aider 还设了个容差：只要误差在 15% 以内就接受，不追求极致精确（省时间）。

#### 本项目怎么实现（不需要任何新依赖）

关键洞察：**Aider 需要现抽标签，你不需要。**

你的数据库里已经有 `symbols`（符号）、`refs`（调用）、`ref_targets`（调用指向谁，带可信度）。
直接建图就行：

```
输入：projectId、当前符号、用户勾选的补充方法、token 预算

1. 建图
   节点 = symbol
   边 = ref_targets（exact 权重 1.0，inferred 0.6，heuristic 0.2）

2. personalized PageRank
   当前方法 ×50、用户勾选的方法 ×10、同文件 ×5、其余 1
   迭代 20 次左右（5000 个符号量级够用）

3. 取 top-N，渲染成骨架
   每个符号一行：qualifiedName + signature + 文档注释首行
   按文件分组缩进

4. 二分 N，让骨架总字符数 ≤ 预算
```

伪代码对应的真实落点：新增 `src/lib/repo-map.ts`（纯函数，可以 `node --test` 直接测），
然后在 `explain-prompt.ts` 和 `question-context.ts` 拼提示词的地方插一段
`### 项目结构（按相关度排序，不是完整源码）`。

#### 两个必须注意的坑

1. **性能**：5000 个符号的图，PageRank 迭代 20 次是几十万次运算，浏览器端做会卡。
   建议放在服务端，和现有 API 一起返回。
2. **口径**：必须明确告诉用户"这是按静态引用排的序，不代表执行顺序，也不代表代码质量"。
   否则又变成"假装准确"。

### 4.2 稳定符号 ID：把座位号换成身份证

#### 问题回顾

2.3 节说过：重扫后 `symbols.id` 会重新发号，导致书签、讲解缓存、问答记录全部要靠猜来找回。

#### 类比

- **座位号**：3 号座。换一间教室，3 号座坐的是别人。
- **身份证号**：不变。走到哪都是你。

#### SCIP 的方案

SCIP 是一个"代码符号编号协议"。它的编号长这样：

```
<scheme> ' ' <manager> ' ' <package-name> ' ' <version> ' ' <descriptors>...
```

官方示例：

```
com/example/MyClass#myMethod(+1).
```

逐段拆开看：

| 片段 | 含义 |
| --- | --- |
| `com/example/` | 命名空间，以 `/` 结尾。这里是包路径 |
| `MyClass#` | 类型，以 `#` 结尾 |
| `myMethod` | 方法名 |
| `(+1)` | **消歧符**：参数个数 +1。因为 Java 里 `foo()` 和 `foo(int)` 是两个方法 |
| `.` | 方法以 `.` 结尾 |

符号的分隔符是有讲究的：`/` 命名空间、`#` 类型、`.` 术语/方法、`()` 参数。
这样光看字符串就知道层级关系。

#### 为什么必须带参数个数

```java
class UserService {
    void save(User u) { ... }
    void save(List<User> users) { ... }
}
```

两个都叫 `save`。如果编号只用 `UserService#save`，它们就撞车了。
带上参数个数，变成 `save(+1)` 和 `save(+1)`——还是撞。

所以 SCIP 的完整做法是：先试参数个数，撞了再用更细的消歧（比如参数类型的哈希）。
对本项目来说，**先用参数个数，撞车时退回"源码前 8 个字符的哈希"**，够用了。

#### 本项目怎么用

```
code-atlas  python  .  0  src/app/service.py/OrderService#pay(+1).
   ↑scheme   ↑mgr  ↑pkg ↑ver  ↑namespace        ↑type   ↑method
```

- `scheme` 固定 `code-atlas`
- `manager`/`package`/`version` 对个人本机工具意义不大，填占位符
- `namespace` 用**项目内相对路径**（这样移动文件夹会变，但改名不会）
- 类型用 `#`，方法用 `(...)`，重载用参数个数消歧

#### 为什么这一步能"净删代码"

做完之后：

| 位置 | 现在怎么找回符号 | 之后 |
| --- | --- | --- |
| 书签 `learning-store.ts` | `anchorKey`（路径+类型+限定名+源码摘要） | 直接按 `stableId` 查 |
| 讲解缓存 `rescan-explanations.ts` | 指纹匹配 + 一堆边界判断 | `stableId` 命中即保留 |
| 问答记录 `questions-server.ts` | `identity` 字符串 + 歧义处理 | 同上 |

**这是整份报告里唯一一个"做完之后代码变少"的改动。** 其他都是加功能。

#### 代价

需要一次数据库迁移：加 `symbols.stable_id` 列、建唯一索引、给老数据回填。
指纹版本号要从 1/2/3 升到 4，旧指纹保留只读回退。

### 4.3 认知复杂度：为什么"圈复杂度"不够用

#### 问题

本项目现在用**圈复杂度**（Cyclomatic Complexity，简称 CCN）给方法排序。
CCN 的定义是"独立路径的数量"，算法很简单：`1 + 判定点个数`。

问题是它对"读起来累不累"几乎没有区分度。看两段代码：

**A：平铺 5 个 if**

```python
if a: handle_a()
if b: handle_b()
if c: handle_c()
if d: handle_d()
if e: handle_e()
```

CCN = 1 + 5 = **6**

**B：嵌套 5 层 if**

```python
if a:
    if b:
        if c:
            if d:
                if e:
                    handle()
```

CCN = 1 + 5 = **6**

**分数一样，但 B 明显难读得多。** 因为读 B 的时候，你的大脑要同时记住 5 个条件；
读 A 的时候，看完一个忘一个。

#### SonarQube 的解法：认知复杂度

核心思路有两条：

1. **嵌套要罚分**：同样一个 `if`，嵌套在第 3 层比在第 1 层更费脑子。
2. **打断线性流程要罚分**：`break`、`continue`、`goto` 让你没法顺着读下去。

具体规则：

| 结构 | 加分 |
| --- | --- |
| `if` / `else if` / `else` | +1 |
| 三元表达式 `a ? b : c` | +1 |
| `switch` | +1 |
| `for` / `while` / `do-while` | +1 |
| `catch` | +1 |
| 每段连续的 `&&` / `||`（`a && b && c` 算 1 次，不是 2 次） | +1 |
| 递归环里的每个方法 | +1 |
| **上面这些结构，如果嵌套在别的结构内部** | **额外 + 当前嵌套层数** |
| `try` / `finally` / 普通 `break` / `continue` | **不加分** |

所以 B 的分数是：

```
第 1 层 if  → 1 + 0 = 1
第 2 层 if  → 1 + 1 = 2
第 3 层 if  → 1 + 2 = 3
第 4 层 if  → 1 + 3 = 4
第 5 层 if  → 1 + 4 = 5
合计 15
```

A 的分数是 5，B 是 15。**这才符合直觉。**

#### 实现成本

每个语言插件在算 `metrics` 的时候，多维护一个 `nestingDepth` 变量：
进入 `if`/`for`/`while`/`try` 时 +1，出来时 -1。加分时用 `1 + nestingDepth`。

大概每个语言 20 行。八个语言加起来不到 200 行。

然后 `summary.ts`（静态摘要）、`project-insights.ts`（学习排行）、
`symbol-search`（排序选项）各接一下就行。

#### 一个必须注意的地方

**两种复杂度不能相加，也不能互相比较。** 同一个方法 CCN=6、认知复杂度=15 是完全正常的。
UI 上要写清楚口径，否则用户会以为哪个算错了。

### 4.4 骨架压缩：怎么把 1000 行压成 100 行还不丢信息

#### 问题

Repo Map 告诉你"这 30 个方法很重要"，但你真把它们全文塞给模型，
30 个方法 × 平均 40 行 = 1200 行，轻松吃掉几万 token。

#### 类比

你需要了解一本书的内容。

- **全文**：太厚，读不完。
- **目录**：只有标题，不知道每章讲什么。
- **带摘要的目录**：每章标题 + 一句话摘要。**这个最好。**

骨架压缩就是做"带摘要的目录"。

#### Repomix 的做法

用 tree-sitter 把方法体替换成一个符号 `⋮----`，只保留：

- `import` 语句
- 函数/类的签名（名字、参数、返回类型）
- 文档注释
- `interface` / 类型声明（这些本身就是"契约"，不能删）

官方给的例子：

```typescript
// 压缩前
const calculateTotal = (items: ShoppingItem[]) => {
  let total = 0;
  for (const item of items) {
    total += item.price * item.quantity;
  }
  return total;
}

// 压缩后
const calculateTotal = (
  items: ShoppingItem[]
) => {
⋮----
```

官方口径：**省约 70% token**。

#### 本项目怎么实现（比 Repomix 更简单）

Repomix 需要重新解析，因为它是通用工具。你不需要——`ExtractedSymbol` 里已经存了：

- `startIndex` / `endIndex`：**展示范围**（含装饰器和 `export` 关键字）
- `defStartIndex` / `defEndIndex`：**定义范围**（真正带函数体的那个节点）

所以"签名段"和"函数体段"直接就是两段字符区间：

```
签名段 = source.slice(startIndex, defStartIndex)   // 装饰器 + export + 签名
函数体 = source.slice(defStartIndex, endIndex)     // 需要被替换掉
```

策略：

- **当前方法**：保留全文（它才是主角）；
- **其他方法**：只留签名段 + 文档注释，函数体换成 `⋮----`。

#### 为什么这个改动风险很低

因为它**只影响"发给模型的内容"**，不影响：
- 数据库存的东西；
- 内容指纹（指纹算的是完整源码，不是骨架）；
- 界面上显示的东西。

做坏了最多是 AI 讲得差一点，不会让数据出问题。

## 第 5 章 为什么不抄另外那些

判断标准只有三条，任何一条不满足就放弃：

1. **会不会引入编译/安装负担？**（这个项目最核心的取舍是"npm install 完就能跑"）
2. **会不会破坏"导入即用"？**（现在导入一个项目不需要任何配置）
3. **运维成本是不是超过了收益？**（这是个人本机工具，不是团队平台）

按这三条筛一遍：

| 想抄的 | 为什么放弃 |
| --- | --- |
| **Sourcetrail 的 clang 索引器** | 违反第 1 条。clang 要装完整 C++ 工具链，Windows 上尤其痛苦 |
| **Sourcegraph 的 Zoekt 索引** | 违反第 3 条。它是为"跨几百个仓库、服务上千人"设计的，你只看一个本地项目 |
| **Semgrep / CodeQL 的规则引擎** | 目标不同。它们找漏洞，你帮人读懂代码。规则语言的复杂度对学习者是纯负担 |
| **Glean 的 facts + Angle** | 违反第 2 条。要学一门新查询语言，而现有 SQLite + Drizzle 已经够用 |
| **Mermaid / D2 当主渲染** | 它们生成静态图，做不到"点节点跳源码""展开节点加载下一层" |
| **code-graph-rag 的图数据库** | 违反第 1、3 条。要跑 Neo4j 或 Memgraph。而 SQLite 的递归查询已经能算循环依赖了 |
| **向量检索（claude-context）** | 违反第 1 条。要引入 embedding 模型和向量库。而且你已经有精确的符号图了，语义检索的边际收益不高 |
| **serena 的 LSP 路线** | 见下 |

#### 单独说 LSP

**LSP**（Language Server Protocol）是编辑器（VS Code 等）和语言服务之间通信的协议。
你按 F12 跳转到定义，就是 LSP 在干活。serena 的思路是：既然 VS Code 能精确跳转，
我直接用同一套协议，何必自己写解析器？

这个思路很聪明，但对本项目有硬伤：

- LSP 要求**目标项目已经装好依赖**（`npm install` 过、有 `node_modules`），
  否则 TypeScript 语言服务器起不来；
- Python 要装 pyright 或 pylsp，Java 要起 JDT server，都是额外进程；
- 现在的体验是"选个文件夹就分析"，用了 LSP 就变成"先配环境"。

所以报告里把它列为"可选增强后端"，并且明确写了**高风险**：
只有在检测到目标项目确实装了语言服务器时才启用，结果单独标注，不覆盖现有结果。

## 第 6 章 想动手的话，从哪开始

### 6.1 最小的一步：一条 SQL 找出"没人调用的方法"

这是整份报告里**成本最低、收益最直观**的功能。

```sql
-- 找出项目内零调用方的函数/方法
select s.id, s.qualified_name, f.path, s.start_line
from symbols s
join files f on f.id = s.file_id
where s.project_id = ?          -- 你的项目 ID
  and s.is_test = 0             -- 排除测试
  and s.kind in ('function', 'method')
  and not exists (
    select 1
    from ref_targets t
    join refs r on r.id = t.ref_id
    where t.target_symbol_id = s.id
      and t.confidence in ('exact', 'inferred')   -- 只算确定和推断
  )
order by f.path, s.start_line;
```

**但直接跑会得到一堆误报**，必须排除三类：

1. **入口方法**——`project-entries.ts` 已经识别出来了（Spring 路由、`main` 函数、Next.js 页面等），
   它们本来就没有项目内调用方；
2. **框架回调**——Vue 模板里的 `@click="handleSave"`、React 的 `useEffect` 回调，
   框架会在运行时调用，静态看不到。`ExtractedCall.origin` 里有 `vue-template` 标记；
3. **接口实现**——接口方法没有直接调用方，但实现类的方法被调用了。

排除之后剩下的，才是真正"孤立的代码"。

**UI 上必须写的免责声明**：静态分析看不到反射、装饰器注册、框架约定，
所以这个列表**不等于"可以删的代码"**。它只是一个"值得看一眼"的清单。

### 6.2 第二个练习：给一个方法算认知复杂度

在 `src/lib/analysis/lang/braced-flow.ts`（大括号语言共用的流程处理）里加一个计数器：

```typescript
// 伪代码
function cognitive(node: SyntaxNode, depth: number): number {
  let score = 0;
  for (const child of node.children) {
    if (isBranch(child)) {
      // if / else if / for / while / switch / catch
      score += 1 + depth;
      score += cognitive(child, depth + 1);   // 子结构嵌套加深
    } else if (isLinearBreak(child)) {
      // 带标签的 break / continue / goto
      score += 1;
      score += cognitive(child, depth);
    } else if (isTryOrFinally(child)) {
      // try / finally 不加分，但内部结构照常算
      score += cognitive(child, depth);
    } else {
      score += cognitive(child, depth);
    }
  }
  return score;
}
```

然后在 `SymbolMetrics` 里加一个 `cognitive` 字段，各语言插件调用一下。

**验证方法**：写两个测试用例（平铺 5 个 if 得 5，嵌套 5 层得 15），
再拿真实项目里最复杂的 5 个方法人工看一遍，确认分数符合直觉。
