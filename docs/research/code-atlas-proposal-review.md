# 开源调研建议复核：Code Atlas

复核日期：2026-10-20。依据用户提供的 4.1–4.4 节、当前仓库代码，以及配套的上游源码与规范核实记录。

上游细节与直接出处见 [开源方案事实核验](./open-source-claims-verification.md)。以下优先级与落地策略是基于这些证据作出的项目判断，不是上游项目的承诺。

## 结论与优先级

四个方向都有参考价值，但不能直接作为实施规格。最值得先做的是**有限范围的上下文增强**：相关方法的签名骨架，加明确标注可信度的直接调用方/被调用方。PageRank 应通过效果比较后再决定是否加入。认知复杂度可作为第二阶段的学习辅助指标。稳定符号身份值得统一设计，但“用 stableId 命中就保留缓存”和“净删现有匹配逻辑”不成立。

建议顺序：**基础骨架与局部上下文 → 评测后扩展 Repo Map → 可解释的认知复杂度 → 有明确需求时统一跨扫描身份**。不必为这些能力整体引入 Aider、Repomix 或 SCIP 索引器。

## 4.1 Repo Map：方向正确，不能把排序当成系统理解

当前自动讲解确实只发送当前节点源码、签名、注释和调用事实，并且源码超过 14000 字符会截断。这部分问题判断准确。但当前问答已经支持用户主动选择补充方法，服务端校验其项目归属后发送源码；“整个 AI 功能只能看到一个方法”不符合现状。

上游机制基本准确，但 [Aider 源码](https://github.com/Aider-AI/aider/blob/main/aider/repomap.py) 的 ×50 是聊天文件作为引用者的出边权重，不是给节点最终得分乘 50；personalization 作用于迭代，不只决定初始分数。它还会把文件分数分配给具体定义。15% 容差也可能接受略微超预算，不能据此保证硬上限。

证据：`src/lib/explain-prompt.ts`、`src/app/api/projects/[id]/symbols/[sid]/explain/route.ts`、`src/app/api/projects/[id]/symbols/[sid]/questions/route.ts`。

最有用的增量是补充“谁调用当前方法、当前方法依赖谁、它所属的类型/文件”，而不是先找全项目最重要的函数。普通调用方向 A→B 的 PageRank 会倾向把分数传向被调用的工具方法，未必能解释 A 在业务中的作用。应保留直接调用方，并按问题目标考虑反向关系或单独名额。

数据库可以复用，但它与 Aider 的标签图不等价。本项目主要记录调用/构造/JSX 等关系，README 明确说明函数作为参数传递不会产生引用；类型使用、字段引用和部分动态注册也不完整。它能构建的是静态调用骨架，不能声称覆盖项目全部依赖。HTML/JSON 的包含关系也不能加入调用图冒充调用。

原文的 `1.0/0.6/0.2` 和 `50/10/5/1` 是待验证的产品参数，不是准确率。候选应分摊同一调用点的总权重，避免候选越多“投票”越多；首版可以只用确定和推断边，猜测单独展示。当前方法和用户明确选中的方法应保底保留，不能只靠软权重竞争预算。

PageRank 的通俗介绍漏了阻尼、重启与无出边节点处理；只反复沿边分发不保证收敛。实现复杂度应按迭代次数乘以节点与边数量估算，不能只看符号数。“5000 个符号在浏览器一定会卡”“20 轮一定够用”均无测量依据。放服务端便于统一查询和缓存，但也要避免阻塞 Node 请求线程。项目当前限制是 5000 个参与分析的文件，符号数量可能远大于 5000。

预算应覆盖系统提示、当前源码、手选补充、历史对话、静态事实及输出预留。字符数是估计，不是 token 数。按序累计预算就能做首版；二分只是一种减少重复渲染的优化，并非必要条件。

房间类比中的“旁边是财务部，所以大概开预算会”恰好展示了风险：位置相关性不证明业务用途。模型仍需标注信息不足。

## 4.2 稳定符号 ID：身份与缓存新鲜度必须分开

“数据库整数 ID 在重扫后变化”准确。“书签、缓存、问答全部靠猜找回”不准确：现有代码已经分别实现内容与身份匹配，并在歧义时停止关联。

- `learning-store.ts:46`：按路径、语言、类型、限定名筛候选；源码摘要可唯一匹配时恢复；唯一节点正文变化时标记 changed；歧义不自动选。
- `rescan-explanations.ts`：按内容指纹恢复，旧讲解保留绝对位置检查，重复定义拒绝不唯一匹配。
- `questions-server.ts:22`：身份与 fingerprint 分开；历史保留并标记 outdated，来源源码还需匹配摘要。
- 个人笔记也复用学习锚点。统一身份设计不能只迁移报告中列出的三个消费者。

**stableId 回答“这是哪个方法”，fingerprint 回答“当时讲解依据是否仍有效”。** 同一个 `pay()` 从原价扣款改成折扣扣款，身份可以不变，但旧讲解必须失效。即使身份与正文未变，提供给模型的依赖事实、补充上下文或提示词改变，也可能使缓存失效。

因此 `stableId 命中即保留` 会返回过期解释，不能采用。稳定身份可减少候选检索与重复实现，但不能删除内容核对、旧行号兼容、歧义处理和引用片段验证。

参数数量不能区分同参数数目的重载；若用方法体哈希消歧，编辑正文反而使身份变化。“源码前 8 个字符的哈希”信息量更不足，且无法区分相同前缀的声明；如果原意是完整源码哈希截取 8 位，也仍有截断碰撞和正文编辑改变身份的问题。优先考虑语言、相对路径、容器、节点种类和规范化声明签名，再制定无法消歧时的保守策略。

更直接的事实错误是：[SCIP 协议](https://github.com/scip-code/scip/blob/main/scip.proto) 没有规定 `(+1)` 表示参数个数，也没有“先参数个数、冲突后类型哈希”的统一算法。它定义的是方法消歧字符串；具体生成策略由索引器决定。方法描述符是 `name(disambiguator).`，参数描述符另有语法，不能把二者混在一起。

相对路径仅能使仓库根目录迁移不影响身份；文件改名、移动，或符号改名都会改变这种键。它不是天然的“身份证”。如需跨重命名追踪，须另做历史映射；SCIP 格式本身不会完成这件事。唯一索引应按项目隔离，例如 `(project_id, stable_id)`，否则多个导入项目的同路径同声明会冲突。

增加 stable_id 数据列不天然要求讲解指纹升到 4。是否升级取决于模型输入与指纹语义。当前代码的 1/2/3 是普通代码、HTML/JSON、带装饰器 JS 等条件分支，并不是数据库依次经历的三个迁移版本。

## 4.3 认知复杂度：有用，但成本和规则被简化

平铺 5 个 if 与嵌套 5 层 if 的例子正确，分别得到 5 与 15，能补充当前圈复杂度无法区分的嵌套负担。它适合帮助选择学习对象，不宜成为跨语言质量评分。

“每遇到结构就加 1+depth”不等于 Sonar 规则。else/else-if、三元表达式、switch、逻辑运算符序列、嵌套函数、带标签跳转和递归分别存在例外；try/finally 也不能直接当普通控制结构增加深度。原文先称 break/continue 要加分、后称普通 break/continue 不加分，前后表述需要收紧。

真正的递归环涉及跨方法调用图及环检测，本项目的推断与猜测调用还会带来不确定性。若首版只做 AST 内的结构度量，应明确不包含跨方法递归环，而不能冒称与 Sonar 完全一致。

依据：[Sonar 官方认知复杂度白皮书](https://www.sonarsource.com/docs/CognitiveComplexity.pdf)，特别是规则说明与附录。

现有度量集中于 `src/lib/analysis/util.ts:73` 的 `computeMetrics`，语言插件提供节点判断。适合沿用“公共遍历 + 语言配置”，而不是八种语言各复制一份计分器。Vue 复用 JS/TS 解析；HTML/JSON 不属于适用的方法指标，“八个语言各 20 行”不能用于估算工作量。

还需要考虑 `SymbolMetrics`、旧 JSON 指标缺失、重新扫描、搜索 SQL、排序分页、摘要、排行和解释缓存。旧值缺失应显示未计算，不能默认为 0。若认知复杂度进入模型事实，或直接新增到当前整体参与哈希的 metrics 对象，都需检查缓存兼容。

## 4.4 骨架压缩：可优先试做，但切片公式错误

保留当前目标源码、为自动发现的外围方法提供签名和短注释，很适合控制上下文开销。但骨架是有损摘要，不能承诺“1000 行压成 100 行不丢信息”：返回行为、状态变更、异常和具体调用细节都会丢失。签名与注释不能证明实现。

[Repomix 官方压缩文档](https://repomix.com/guide/code-compress)仍把此功能标为实验性；本次查阅的官方页面和 README 未找到可支持“约省 70%”的基准或保证。因此不能把该数字当成本项目的预期收益，需按语言和样本实测。

`src/lib/analysis/types.ts:60` 明确说明 `defStartIndex` 是**定义节点起点**，不是函数体起点。例如普通 Python `def` 的 `startIndex` 与 `defStartIndex` 通常相同。原文 `source.slice(startIndex, defStartIndex)` 会是空串；有装饰器时通常也只能留下前缀，签名被删除。

最小实现可以直接用已有 `signature + decorators + docstring` 生成文字骨架。但多个插件把 signature 压成一行并截到 200 字符，复杂泛型和长参数列表可能不完整。若需要无损保留声明头，需获取真正的 AST body.startIndex，或在提取阶段显式保存函数体/声明头边界。不能从 defStartIndex 猜。

“已有数据等价于 Repomix 完整骨架”也不成立。README 明确指出 TypeScript 重载、接口方法签名等无函数体声明目前不作为符号；数据库骨架不能恢复未提取的信息。首版应称“已提取符号摘要”，不要承诺完整 import/type/interface 契约。

压缩对象优先选择自动补充的背景方法。用户手选的补充方法可能正是理解实现的必要依据，不宜一律替换为签名。问答引用目前映射到实际源码片段行号，骨架文字需要与可点击源码引用分开，避免把骨架第 3 行链接到源码第 3 行。

**“不影响指纹”这一结论错误。** 只要新增 Repo Map、改变实际提供的上下文，或切换全文/骨架语义，就应版本化上下文策略，并把实际使用的上下文摘要纳入缓存有效性判断。当前 fingerprint 只涵盖目标源码、符号元数据及调用事实，不涵盖新增地图中的其他符号签名和注释。否则其他方法变了，旧讲解仍可能被误判有效。可以继续哈希完整来源以保守失效，但也必须纳入相关来源和呈现策略。

## 建议的首个可评审版本

1. 在服务端建立统一上下文构建入口；自动讲解、应用内问答与复制上下文分别接入，保持来源归属。
2. 当前方法保留现有源码策略；手选补充优先保留实现，自动背景补充先用签名骨架。
3. 固定保留少量直接调用方、被调用方和容器信息，按文件分组，清楚说明可信度和省略范围。
4. 统一总预算并记录实际上下文摘要、策略版本。地图顺序稳定，使用项目扫描版本隔离图缓存。
5. 先用模拟后端验证提示词、归属、引用、过期标记与重扫行为。整理固定阅读问题，比较“当前版本、局部上下文、局部上下文加 PageRank”的实际解释质量，再决定是否引入算法复杂度。

本次为评估，仅新增调研文档；未改产品实现、数据库或运行中的服务，未调用真实模型。
