# 大项目分析与搜索性能优化

2026-10-28。本轮由 Sol / Terra 收集证据，Astra 设计与复核，Sol 实现解析优化，Terra 实现搜索优化。

## 范围与依据

- Java 调用解析原先为每个已定位目标的调用执行 `recs.flat().find(...)`，重复分配并遍历整个项目的符号数组。现在一次构建符号 ID 索引，重载查询复用文件内的容器索引；Go / Java 导出查找也只筛选同名顶层符号。保留候选顺序、可信度、分数、原因及同包歧义处理。实现见 [resolve.ts](../src/lib/analysis/resolve.ts)。
- 普通结构化搜索原先在计数与结果查询中分别统计全项目调用方。现在无调用方阈值的计数不做这项统计；不依赖调用方筛选或排序的结果先筛选、稳定排序和分页，再通过现有目标索引统计当页调用方。阈值包含 `minExactCallers=0` 的查询，以及按确定调用方数排序的结果，仍先统计再分页。实现见 [symbol-search-sql.ts](../src/lib/symbol-search-sql.ts)。

没有新增依赖、持久缓存、表结构或数据库迁移，也没有更改解析规则、页面交互或生成任务生命周期。

## 可复现测量

从仓库根目录运行，均使用临时内存数据，不操作用户数据库，不执行被分析的源码，也不调用真实模型：

```bash
node --experimental-strip-types tools/benchmark-resolve.ts --compare-ref 6f58250
node --experimental-strip-types tools/benchmark-search.ts
```

解析基准只计 `resolveProject`，不包含 Tree-sitter 抽取和 SQLite 入库。它解析一次 Java 模板后构造多个文件，每个文件含 22 个符号和 100 次调用；每个规模运行三次，取中位数，并与基线提交完整输出深比较。本机复测：

- 25 文件、550 符号、2500 调用：31.3 → 4.6 毫秒。
- 100 文件、2200 符号、10000 调用：359.7 → 9.8 毫秒。
- 250 文件、5500 符号、25000 调用：2067.2 → 13.4 毫秒。

搜索基准使用内存 libSQL、与当前表结构相同的相关索引、8000 个方法与 100000 条引用，查询 `service7999`。热身后各运行七次，取中位数。对照为当前保留的全量聚合路径，以 `minExactCallers=0` 保持相同的方法范围和完整结果，并非加载旧提交执行。本机复测：

- 计数：全量聚合 227.57 毫秒，当页优化路径 5.12 毫秒。
- 结果：全量聚合 233.37 毫秒，当页聚合 7.05 毫秒。
- 查询计划显示先物化当前页，再使用 `ref_targets_target_idx` 按目标查找引用。

这些数字只代表上述夹具和指定阶段，不代表所有语言、查询或整个导入流程的通用提速；按调用方排序或筛选仍需要全量统计。两份脚本输出当前环境的实测结果，不设置固定耗时断言。

## 正确性与链路验证

- Java / Go 回归覆盖跨文件、类容器与语言隔离，重载候选顺序、可信度及同包歧义；三个 Java 基准规模与基线的完整解析输出一致。
- 搜索回归覆盖三页及越界页、多种排序方向、零调用方、重复调用、测试调用方、三档交叉统计及跨项目干扰。
- 另用基线提交的原始 SQL 做一次性差分验证：384 组筛选、排序、分页组合的总数与完整结果逐项一致。
- 52 项相关解析、搜索、调用树与解析器重载测试，改动文件 ESLint、类型检查和生产构建通过。
- `RUN_INSIGHTS_E2E=1` 的项目查询集成测试通过，使用其独立临时数据库、源码和应用，覆盖搜索、项目隔离、重扫及学习记录保留。
